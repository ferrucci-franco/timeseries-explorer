# Time Series Explorer v0.6.0

A multi-year record now answers both of its questions: at what level each year sat, and how much each year accumulated. The temporal profile gains a **Multi-year** period laid out along the real timeline, and the integral gains **Group by: day, week, month, year** — one column per calendar period. Integral units read right at last: a rain gauge in `mm/h` totalled over hours says `mm`, not `mm/h·h`. And **Settings → Number format** lets you choose the decimal and thousands separators instead of taking whatever the interface language implies.

## Calendar periods

- **Temporal profile → Multi-year.** Every other period folds the recording onto a template — the hours of a day, the months of a year. This one does not: its bins are the calendar years the data spans, in order, along the real timeline. Its sub-period is the UTC day, so each year carries the mean of its daily means, and ±1σ measures how much the days inside that year differed from one another.
- **Integral → Group by: Day, Week, Month, Year.** Each calendar period (UTC) is integrated on its own: one column per period, one colour per signal. This is what turns a rainfall record in mm into the accumulated rainfall of each year, or a power in MW into the energy of each month. **Whole range** is still the default.
- **Grouping never changes the total.** The periods are exact and share their edges to the millisecond, so the columns always add back up to the whole-range total shown in the summary. The series' nominal step is handed down to every window, because a single day holds too few rows to establish one on its own, and each window is read with a neighbouring sample on each side.
- The grouped totals go to the **CSV export** with their periods. The pie is hidden while the totals are split by period and more than one signal is shown, since a pie of several signals over several periods says nothing. A grouping that would make more than 2000 periods asks for a coarser period or a narrower range instead.
- **Very large files need no second pass.** Every calendar period is a whole number of UTC days, so the grouping is a partition of the per-day partials the file already gave up — on a file opened through DuckDB, grouping costs no new query.
- Both features need a calendar time axis, and both were checked against hand-computed numbers in a real browser.

## Integral units

- **A per-time unit cancels against the integration.** `mm/h` integrated over hours is `mm`; `m³/s` over seconds is `m³`. Only an exact match cancels: `m³/s` integrated over **hours** still reads `m³/s·h`, because that one needs a factor of 3600 and a label hiding it would claim a number nobody computed. A rain gauge declared as the rate it is — `mm/h` — now totals to `mm`.
- **Automatic scaling is taken only when the unit absorbs it.** 2400 MW·h reading 2.4 GW·h is a gain: the unit carries the decade. When the unit cannot fold it, the prefix only displaced the decimal point and left a `×10³` in the axis title to be carried back to every bar — and where thousands are grouped with a dot, "1.311" *is* the number it stands for. A prefix pinned by hand is still applied as asked, with its leftover decade stated.
- Seven years of hourly rainfall now read 1,311 / 1,939 / … mm on an axis labelled `Integral [mm]`, against 1.311 / 1.939 on `[?]·h ×10³` before.

## Number format

- **Settings → Number format** overrides the **decimal separator** and the **thousands separator**. Both default to *Automatic (from the language)*, which is exactly what each language did before, so nothing moves until you open it.
- The interface language still ignores the operating system on purpose — a browser in English must not print "16,777,216" inside a Spanish sentence — but the language is no longer the only say: the convention of the interface and the convention you work in are not always the same.
- *Automatic* also keeps each language's rule about **when** to group: Spanish and Italian leave a four-digit number alone and group from five. An explicit choice groups from four, because choosing a separator is asking to see it. The two separators can never be the same character — the colliding option is disabled in the menu rather than discovered afterwards.
- It reaches everything the app writes for reading, including Plotly's own tick labels and hover values. It reaches neither the **CSV export**, where comma decimals beside comma delimiters make a broken file, nor number input fields, which the browser parses by its own rules.

## Fixes

- **CSV:** a logger that writes `NaN` for an absent sensor had its first data row taken for the header and its all-NaN columns read as text. `NaN` cells are now ignored by the header and numeric-column checks, as an empty cell already was.
- Counts written in messages — points, samples, cells, series — followed the browser's locale instead of the app's; they now follow the interface language and the Number format settings.
- The Number format fields are stacked one per row so the longest option, *Automatic (from the language)*, is readable before the menu is opened.

## Desktop capabilities

- Fully local, offline application and bundled processing libraries.
- External documentation links open in the operating system's default browser.
- No classic Electron menu or secondary Electron browser windows.
